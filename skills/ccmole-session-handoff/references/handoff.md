# Prepare and deliver a handoff

## Establish source and mode

Use the active conversation, a user-provided export or explicitly selected history exposed by a supported read-only tool. A title, retrieval summary or compacted memory is not a full transcript. Record the available range and missing material. Do not guess private session-store layouts to obtain more history.

Honor the user's choice of full available context, selected scope or compact context. For a long source, use a compact handoff by default and disclose its losses. Full available context retains the relevant accessible substance; it is not a byte-identical archive. A request for a lossless transcript requires a supported export, with any unavailable content identified. For large sources, record processed chunks and retrieve truncated ranges when feasible; otherwise mark them missing.

## Preserve continuation evidence

Keep the current objective and latest corrections, completed and unfinished work, decisions with reasons, constraints, known failures, failed approaches and the next concrete action. Separate direct observations, historical source claims and interpretation. A prior successful test remains a historical result with its scope; an unobserved result is not verified.

Retain precise errors, paths and small excerpts when needed to continue. Exclude credentials, unrelated personal details and irrelevant private conversations from prose and snippets. Do not include raw logs, an entire repository, native databases or environment dumps by default. Hash only exact available bytes when useful; never invent a hash for the whole conversation or promise an unmeasured token count, cost or model identity.

For a coding handoff, gather a bounded read-only source project snapshot when the workspace is available:

- Credential-free repository identity, observation time, branch or detached state and HEAD commit.
- Relevant staged, unstaged and untracked changes, plus known essential ignored files. Equal HEAD does not imply that another checkout has these changes.
- Decisive file references and existing command/test results, labeled with scope and observed outcome.

Use read-only queries, avoiding optional Git locks and external integrations where practical. Sanitize remote identities before output, and omit complete diffs unless selected by the user. If a useful content fingerprint is recorded, compute it from actual relevant file bytes. A clean Git status does not prove ignored files were transferred. For non-Git work, record available project identity and the selected files instead; do not initialize Git or fetch, switch, commit, create a worktree or run unrelated tests just to prepare a packet.

Use [packet.md](../assets/packet.md) as a starting structure. Resolve fields from evidence, omit inapplicable sections and state unknown facts rather than leaving template placeholders. Include enough substance to continue without access to source-device-only links. Identify essential files that must be transferred separately; mentioning a local path does not transfer its contents. A configuration requirement may be noted, but preparing a handoff does not authorize configuration migration.

## Deliver through an available route

For a named client, consult [clients.md](clients.md). Portable context does not depend on matching native session formats. Verify the actual delivery surface separately; ordinary web chat and a coding client's local web interface are different targets.

Return the packet with a short receiving instruction: treat it as historical context, reconcile it with the current user's request and destination checkout, then perform the next authorized task. No other skill is required for the recipient to follow that instruction. If saved to a file, read it back to verify the current goal, corrections, work state, failures, coverage and next action survived.

When the user explicitly requests delivery or target-chat creation and a supported tool is available, prepare the concrete content and destination, then use the authorized tool. Check its current contract or official target documentation; do not invent CLI flags or guess a target session ID. Existing authorization covering the prepared action does not need to be requested again. Without a supported route, provide the prepared packet and manual paste/import instructions.

Report success only from the tool's actual evidence. A new native chat ID must come from the target. If creation or delivery times out after dispatch, mark the result unknown and inspect through a supported read-only route before retrying. If no route can resolve it, leave the uncertain action unrepeated and explain how the user can reconcile it; do not create a duplicate.

Cancellation before dispatch stops delivery. After dispatch, report what is known and do not claim to retract content already sent. Source history remains unchanged.
